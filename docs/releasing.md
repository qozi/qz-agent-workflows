# 发布与验收

发布仓库为 `qozi/qz-agent-workflows`。当前 Skill 源码版本为 `2.0.0`，发行标签为 `v2.0.0`；源码中的版本号本身不是发布证据，实际结果、固定提交及验证范围以对应 GitHub Release 为准。

## 发布前

1. 确认 GitHub owner、仓库公开性、源码提交、发布标签、备份方式和本次提交/推送/发布授权；这些不是开发授权的隐含部分。
2. 运行根 README 的本地检查及固定版标准安装器集成验证，记录 Node、安装器、源码 SHA 或未提交快照摘要、命令和限制。
3. 在获准安装的 OpenCode 新会话中确认 Skill 可实际加载，并用 `/dev-takeover 仅检查 <无敏感信息的旧方案>` 核验默认模式、来源读取和命令行为。静态检查或安装成功不能替代这项验收。
4. 审查全部待发布差异、MIT 授权、版本说明及发行清单；禁止机器路径、密钥、原始对话、本地备份、完整全局配置和需求状态材料进入发布。
5. 检查 `.dev-work/` 既被业务 Git 忽略又未被跟踪。不要用 `git add -f` 绕过；旧版已经跟踪的材料须另获迁移批准。

## 发行边界

`node scripts/check.mjs` 输出静态分发载荷的白名单及 SHA-256 摘要。载荷是 README、CHANGELOG、LICENSE、安装/发布说明、`skills/dev-workflow/` 完整资源与 `adapters/opencode/` 接入材料；不包含 `.dev-work/`、测试现场、备份或用户配置。

Git 仓库还保留 `AGENTS.md`、检查脚本和测试，便于贡献与验证；它们不是 Skill 安装单元。标准安装器只负责选中的 Skill，不会自动安装 adapters 或执行接入说明。当前不生成 npm 包或自有发行压缩包。

## 经批准发布后

1. 固定到批准的源码提交和版本标签，分别记录代码交付与流程资料证据，不把文档提交当业务版本。
2. 用临时 HOME 和 README 指定的固定版安装器，从真实远程仓库的固定标签或提交安装；核对完整资源、版本、MIT 及适配入口。远程安装单独记录，不复用本地来源的成功结果。
3. 发布说明保留真实会话加载、操作系统覆盖和失败场景的已验证范围，不将模拟权限失败或静态断言宣传为完整平台保证。
4. 发布或合并不等于用户已启用，也不授权清理工作区。保全唯一流程资料及未提交内容后，清理仍需另行授权。

## 可选 npm CLI

仅当标准 Skill 安装方案不能满足已确认需求时另行立项。必须先确认 npm scope、运行环境、自动化边界和发布授权，并覆盖 dry-run、冲突、备份、恢复与卸载归属；不得通过 postinstall 静默修改家目录。
