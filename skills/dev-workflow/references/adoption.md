# 安装与项目接入

## 共享安装

将整个 `dev-workflow/` 目录作为一个版本单元维护，从发布源码仓库的固定版本安装到其他机器。`skills/dev-workflow/` 是发布源码，安装目录是发行副本；本地修改先比较，不自动覆盖或反向同步。不要把项目需求材料写进共享 Skill 目录。

OpenCode 支持发现 `~/.agents/skills/dev-workflow/`，也支持其原生 Skill 目录；实际目标以选定安装器版本和安装范围为准，安装前核对，不能假定本机已安装。其他工具应查其实际 Skill 发现规则，不推断所有工具都支持同一路径。工具支持配置额外 Skill 目录时可指向同一来源，避免维护内容副本；本仓库首轮仅正式适配 OpenCode。

安装时核对固定来源、版本及完整资源，已有安装内容完全相同则跳过；有本地差异先停止并确认处理方式。修改前备份，缺权限、资源不全或失败时停止，不用强制覆盖绕过。标准安装器不保证替用户安全处理本地冲突。安装 Skill 与接入启动规则、命令分开授权，不初始化业务项目。发布源码仓库另提供 `adapters/opencode/` 和 `docs/agent-install.md`；这些是单独接入材料，不是已安装 Skill 的运行依赖，本节保留独立可用的规则与项目接入说明。

OpenCode 新增或修改 Skill、启动规则及命令后退出并重启，让新会话重新加载配置。当前会话不能以目录存在或文件已修改为由声称启动规则已重载、Skill 工具已加载新版内容。

## 全局启动入口

按平台实际支持的全局规则安装以下片段。OpenCode 可使用全局 `AGENTS.md`；其他工具使用已确认支持的入口。项目 AGENTS 保留项目信息，只放下节的资料引用，不复制全局流程。

```markdown
## 需求开发工作流

开始或恢复软件需求开发前，加载 `dev-workflow` Skill。
先做轻量分流：简单任务直接实现和验证，不初始化需求目录；咨询不自动建档或改代码。
复杂需求恢复主协调工作区的 `.dev-work/workflow.md` 和唯一任务来源，不重复初始化；子 Agent 按派发位置只读资料，完成后回报主 Agent 更新状态。
业务 Git 排除 `.dev-work/`，文档可选独立 Git，不跟随业务分支同步。旧项目资料须获准后迁移，不能另建平行状态表。
只有 Git 项目且确有隔离需要时才建议 worktree，创建前取得用户确认；子 worktree 不创建、复制或链接流程资料。
Skill 不可用时明确说明，不声称已加载；按已存在的项目约定处理。
提交、合并、发布、清理仍受用户授权和平台权限约束。
```

修改全局规则会影响其他项目，应明确告知用户并保留现有内容。本 Skill 不自动修改入口文件。

接入后检查实际入口是否含上述加载规则、平台是否允许发现并读取共享 Skill；重启后在新会话确认实际加载和项目来源解析。安装接管命令不等于普通新需求已经接入，其他工具也需分别检查入口。本段是人工接入检查，不是加载保证或自动拦截机制。

## 完整初始化

只在复杂需求需要且获准初始化时执行；已有资料先恢复。由主 Agent 确认主协调工作区和唯一文档根目录，子 Agent 不执行以下初始化。主协调工作区与业务 main 分支是不同概念。

1. 检查业务 Git 是否存在、现有资料及未提交变更；无 Git 时不擅自初始化业务仓库，也不创建 worktree。
2. Git 项目先检查 `.dev-work/` 是否已跟踪，再在业务根 `.gitignore` 幂等增加 `/.dev-work/`，保留其他规则。检查实际忽略效果和业务索引，不能仅以规则存在推断未跟踪。已有跟踪需单独批准迁移与停止跟踪，不自动 `git rm --cached`。
3. 在主协调工作区创建 `.dev-work/workflow.md` 和索引，按需创建需求材料。已有共享规范及架构只引用。索引、说明和任务记录不进入业务提交。
4. 保留工具 init 生成或项目已有 AGENTS 的项目内容，仅补一次短引用；不要为了这个流程自动运行工具 init、重写整个 AGENTS 或改变业务架构说明。
5. 用户选择文档独立 Git 时，再检查并在准确的资料目录执行 `git init`，见下节；未选择则保留本地资料并说明备份责任。更新资料不自动授予文档或业务仓库提交权限。
6. 确认主 Agent 可维护、子 Agent 可通过派发的只读路径或获准摘录理解任务；记录无法跨机器共享的限制。未通过不宣称初始化完成。

建议的项目 AGENTS 短引用：

```markdown
需求协作资料见 [本地工作流说明](.dev-work/workflow.md)；子工作区缺少此文件时，按主 Agent 派发的资料位置只读访问，不在本地补建。
```

这只是可选流程资料的引用，不应令普通 clone 或简单任务因缺失本地文件而失败。只在需要复杂需求资料时要求主 Agent 提供位置。若子 worktree 的基线尚未包含这行引用，用派发消息补充读取指令，不为同步指针擅自提交业务代码。

## 独立文档 Git

独立仓库是可选项，允许无业务 Git 的项目单独管理文档，但不因此支持业务 worktree。首次初始化必须经过用户选择或已有明确授权。

- 确认目标确为主协调 `.dev-work/`，已有独立 `.git` 或外部文档仓库时复用，不重建、嵌套或覆盖。
- 可执行 `git -C "<主协调工作区>/.dev-work" init`。之后用该目录下的 `git rev-parse --show-toplevel` 确认根目录正是资料目录；初始化前同一命令可能返回业务仓库根，不能把它误认成独立文档 Git。
- 业务存在 Git 时，再核对业务侧 `git ls-files -- .dev-work` 无跟踪条目，`git check-ignore` 实际命中该目录内测试路径；非 Git 业务项目跳过这两项。不能用 `git add -f` 绕过忽略或将资料添加成业务子模块。
- 文档仓库的提交、远程配置、推送和备份分别遵守授权，不修改 Git 用户配置、不创建空提交。独立 Git 的本地历史不等于远端备份，业务 clone、PR 和 CI 都不会自动携带资料。
- 不使用业务 worktree 给文档仓库创建分身，子 Agent 工作区没有 `.dev-work/`，也没有第二个独立文档 Git。

业务 `.gitignore` 未提交时，新 worktree 的基线可能尚无忽略规则；创建前检查基线，报告差异，不擅自提交或在子目录复制文档。子工作区应始终没有流程目录，实际交付前仍检查是否意外产生跟踪材料。

## 项目差异

项目工作流配置放 `.dev-work/workflow.md`，可使用 [workflow 模板](../templates/workflow.md)，不写进项目 AGENTS：

```markdown
## 工作流配置

- 工作流版本：dev-workflow 2.0.0
- 项目标识与业务职责：填写真实项目及共享资料引用
- 主协调资料：指定唯一主协调工作区的 .dev-work/，不等于业务 main
- 文档版本管理：本地目录或用户选择的独立文档 Git；填写文档仓库、分支及运行定位方式
- 项目总索引权威来源：相对于文档根的 README.md 或指定外部系统
- 索引维护者及单一写入者规则：填写持久负责人、运行登记位置和指定方式
- ID 登记可见方式：主协调串行登记，子 Agent 获准只读或接收标明版本的摘录
- 开发规范：已有项目路径；缺失时按需补建 development.md
- 项目架构：已有项目路径；缺失时按需补建 architecture.md
- 业务主分支：实际名称或非 Git 不适用；代码分支与文档分支分开
- 状态系统：主协调任务表或用户指定的外部系统
- worktree：仅业务 Git 项目，确需隔离且用户确认后创建
- 验证命令：填写该项目真实命令
- 提交、合并、发布、清理：分别遵循用户明确授权
- 团队特有阶段门槛：填写已有约定或注明无
```

这些是 Agent 阅读的约定，不是 OpenCode 配置字段或解析器。不要塞进 `opencode.json`，也不要声称它们已自动执行。机器路径、Agent ID 和实际访问权限以运行登记和派发消息为准；跨机器不可访问时不猜路径、不绕过权限。

本 Skill 不搬迁项目产品文档。多项目在共享入口逐项登记业务职责、关联和资料来源；业务文件引用必须注明项目根相对路径，不能误以独立文档 Git 根解析代码路径。跨仓库需求仍只维护一个权威任务表。

尚无索引时先确认资料位置及写入者，不因两个需求并行而分别创建流程目录。项目入口只保留短引用，具体规则留在 workflow.md，索引维护需求导航。

已有需求采用旧版工作流时，入口加载新版不代表已批准迁移。`.dev-changes/`、`dev-changes/`、业务分支内任务表和旧 AGENTS 协作段落按原来源恢复；批准后才迁到 `.dev-work/`、处理已跟踪文件并替换短引用，保留原要求映射及版本证据，不批量改验收或生成第二份实时任务表。

## 旧任务接管入口

OpenCode 可将同一固定源码版本的 `adapters/opencode/commands/dev-takeover.md` 安装到 `~/.config/opencode/commands/dev-takeover.md`；先检查已有命令和差异，取得接入授权后再安装。命令引用共享 Skill，不另存一套流程。Skill 安装器不一定处理仓库适配目录，Skill 本身不会自动注册斜杠命令；未接入时使用下述自然语言入口即可。

```text
/dev-takeover 仅检查 docs/OLD_PLAN.md
/dev-takeover 仅整理 docs/OLD_PLAN.md，代码在分支 feat/example
/dev-takeover 整理并继续 docs/OLD_PLAN.md，复用已有 worktree，不提交不合并
```

这些参数由 Agent 按自然语言理解，不是真实 CLI 选项。默认仅检查；只有明确要求整理或继续时才允许相应修改。

其他工具没有该命令时，可直接要求：“使用 dev-workflow，将指定旧任务按 references/takeover.md 整理并继续。”使用同一流程，无需复制实现。具体规则见 [takeover.md](takeover.md)。

## 自动化边界

本版本提供流程、模板及仓库中单独分发的 OpenCode 接管命令材料，没有附业务项目初始化 CLI、业务 CI 检查器或平台插件。斜杠命令是 Agent 提示入口，不是确定性迁移脚本。所有初始化都先检查现有内容，再使用当前平台允许的编辑工具完成。

需要进一步自动化时，独立开发并验证工具：检查 ID 唯一性、任务状态枚举、依赖引用、已完成证据、链接与测试结果。业务验收、授权和架构正确性不能仅靠结构校验判定。

不要将本地未执行的检查描述成 CI 已生效，也不要承诺自然语言规则能强制阻止违规。
