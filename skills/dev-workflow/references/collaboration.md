# 协调、委派与 worktree

## 委派前

先检查现有 Agent，继续工作优先恢复原任务。遵循宿主平台的代理创建规范，不猜模型、Profile 或授权。

Paseo 中按现有规则先读取 Profiles，再映射配置创建 Agent；未委派的工作由协调者完成，不为了形式强行增加 Agent。

## worktree 决策与创建

1. 判断业务项目是否已有 Git。没有则不用 worktree，不为隔离任务擅自 `git init` 业务项目；文档独立 Git 不满足此前提。
2. 只有大改动隔离、多个需求并行、重叠修改或现有现场存在实际冲突风险时才建议 worktree。简单任务或多个只读 Agent 本身不构成理由。
3. 向用户说明隔离原因、任务范围、基线、分支、工作区和集成方式，询问是否使用 worktree。用户本轮已明确批准同一范围时复用授权并报告，不重复询问；默认开发、继续任务、创建 Agent 都不等于该授权。
4. 获准后检查现有 worktree、代码提交及脏改动，优先复用合适工作区，不覆盖他人修改。明确新工作区只包含所选提交，主工作区未提交实现不会自动携带；需要先提交或迁移时另取相应授权。
5. 只创建代码工作区，不初始化、复制、软链接 `.dev-work/`，也不创建任何独立文档 Git。新工作区缺少任务和本地流程文件是预期状态。若基线仍跟踪旧流程资料，先说明并取得迁移或处理决定，不能自动删除旧文件或声称没有副本。
6. 校验代码分支、基线和资料只读路径，再派发任务；新工作区没有有效 AGENTS 短引用时由派发消息提供说明，不另建流程文档。无法访问主资料时请求主 Agent 提供获准的必要摘录或解决权限，不绕过平台限制。

用户不采用 worktree 时，在现有工作区按文件分工，只有指定集成者执行 Git 写操作；重叠修改串行执行。简单任务不因此升级成复杂流程。

## 派发内容

将以下信息完整交给实现或审查 Agent：

```text
需求/任务：Rxxx / Rxxx-Txx
角色：实现或只读审查
主协调资料：实际可访问的主工作区 .dev-work 绝对路径
必读文件：workflow.md、需求及任务文件的准确路径和对应任务/验收 ID
文档身份：项目和相对路径；可选文档仓库/文档分支/提交或未提交快照标识
权限与时效：仅按获准路径只读；任务范围变更由主 Agent 通知，不依赖旧摘录
所属批次：已定义的 Rxxx-Bxx 或外部系统等价关联
工作分支/worktree：实际已创建的位置
交付目标与完成条件：明确可验证结果
可修改范围：业务代码、已分配长期项目文档
不可修改范围：主协调 .dev-work 全部资料、索引、任务状态及其他 Agent 所有文件
依赖接口：已确认版本；未确认时先同步，不猜字段
验证命令：项目真实命令，附环境限制
Git 权限：明确是否允许提交，默认不自行合并或清理
汇报对象：当前协调者
最终报告：任务 ID、变更文件、代码提交或未提交范围、实际命令/结果、审查问题、限制与阻塞
收尾：通知主 Agent，由其核验、记录证据和更新状态；不得自建任务目录或提交文档 Git
```

共享工作区只设一个 Git 写入者；读操作和互不重叠的文件编辑仍需检查运行中的改动。接口文件先冻结再并行，避免每个 Agent 各自修改同一接口。

## 共享文档写入

| 材料 | 默认写入者 | 其他参与者 |
| --- | --- | --- |
| 项目总索引、需求 ID 登记 | 项目指定的索引写入者 | 提交登记和导航修改请求 |
| 项目开发规范、架构资料 | 各资料指定维护者 | 提出变更并等待授权或合入 |
| 需求身份、授权、范围、验收、阶段门槛、任务状态及集成记录 | 需求协调者 | 提出建议；不自行改范围、批准条件或状态 |
| 主协调 .dev-work 的方案、实现说明、验证和审查证据 | 主 Agent（协调者）汇总维护 | 子 Agent 只读并回报结果，不直接追加或改写记录 |
| 已分配的长期业务文档 | 指定文件或章节写入者 | 不越界修改，不覆盖并发内容 |

同一人可承担多个角色，但需明确指定；需求协调者不自动成为项目索引或共享架构资料的写入者。V001 等证据记录由主 Agent 分配并维护，子 Agent 汇报不直接写主资料。主 Agent 核对实现版本和证据后将任务置为待验收或已完成，不能仅凭“完成”消息勾选。权限声明不是锁，发现并发冲突时暂停相关写入并协调。

## 协调者交接

交接消息列需求 ID、主协调资料实际位置、可选文档仓库及未提交状态、代码位置、当前任务、Agent 状态、验证版本、阻塞、授权和下一步。新主 Agent 确认能读取同一份资料，不在其工作区重建一套。

只有原协调者已停止写入或用户明确裁决后，新协调者才接管。旧 Agent 无法联系时不能假定它已停止；优先通过平台状态或用户确认解决。持久负责人和运行中的 Agent 不必是同一身份。

## 集成

子 worktree 交付需先检查差异与证据，再按批准方式集成提交。不能在含他人半成品的共享工作区执行全量暂存来偷懒。冲突解决后补跑验证。

一个 PR 对应一个清晰主题或批准的批次，不强制一个 commit 一个 PR。PR 审查覆盖全部待合并提交，而非仅最后一个。

批次使用稳定 ID，任务归属以主协调任务表的批次列或外部系统关联为准；PR 引用批次 ID，并说明实际覆盖的任务和代码证据，不复制流程资料到业务仓库。私有本地资料不可对外链接时只提供经允许的必要摘要；如团队要求 PR 内持久审计证据，先确认独立文档共享方式或长期业务证据归属，不假装本地路径可供所有审查者访问。

代码合并和文档更新是两个操作。主 Agent 更新同一资料中的业务 SHA、PR 和启用情况，文档不进入业务合并；文档仓库是否提交另按授权。业务分支改名、合并或删除，只更新代码位置引用，不因此搬迁权威文档。

## 权威来源交接

新版只有资料根目录、独立文档仓库/分支或外部状态系统变更才迁移权威来源；更换主 Agent 可交接同一根目录而不迁移文档。清理承载主资料的工作区前必须保全并解决后续访问，不能把文档迁进业务 main 代替备份。旧版资料仍在业务分支中时，按原约定检查交接，迁往新版须先批准。

1. 明确原/新文档来源、业务代码版本、文档版本、接任维护者和批准依据；不按业务分支刚合并或文件较新自动决定。
2. 暂停原来源的相关写入，检查未提交和未跟踪材料；仅按授权准备候选目标。候选副本尚非第二个权威来源，不在两处继续维护状态。
3. 在目标核对需求材料、批次映射、全部剩余任务、阻塞和验证引用；接受方确认目标可访问。历史代码证据使用可保留的提交 SHA 或可靠归档，不能只依赖待删除分支或本机目录。
4. 由索引写入者发布导航，主 Agent 更新 workflow.md 及需求入口；资料布局改变时才更新项目 AGENTS 的短引用，不复制工作流正文。重新派发可解析的主资料路径，确认所有参与者可读后宣布生效；旧来源不再更新，不双向同步。
5. 在需求 README 的权威交接记录中保留原/新来源、覆盖版本和交接依据；索引自身交接记录留在项目索引。再按单独清理授权处理旧资源。

无更新相关来源的授权、目标材料不完整或新登记不可见时，保持旧权威来源和资源，不宣称已交接；明确阻塞及责任方。独立文档 Git 未推送且无可靠副本时，不以“已提交”宣称备份完成。

## 清理前清单

- 是否有明确授权，且任务确已合并、另处可靠保全或明确放弃？
- 未提交、未跟踪文件以及忽略目录内的必要产物是否已检查？
- 提交是否在目标分支或可靠备份中，不会只存于待删分支？
- 是否停止使用该目录的 Agent、服务和终端任务？
- 是否仍被后续任务、交接或验证路径引用？
- 主协调资料及其独立 .git 是否在待清理目录内？即使被业务 Git 忽略、业务状态干净，也必须检查未提交资料、历史和可靠备份。
- 资料位置变化时，workflow.md、索引、入口短引用及子 Agent 派发位置是否已交接？代码分支删除时，保留的 SHA 和证据是否可复现？
- 是否分别决定删除 worktree、分支和远程分支？
- 平台“归档”是否可能移除物理 worktree，已核实实际语义？

有任何不确定，不强制删除，不以“已完成”代替文件安全检查。
