# 需求拆分与历史材料收口

## 交付批次

批次是能独立审查和集成的最小有意义交付，不必等整个需求结束。批次内可包含多个任务；一个任务应只有一组明确完成条件。

批次使用稳定 ID，例如 R001-B01。需求 README 定义批次目标、具体前置和验收条件；成员归属只在权威任务表的“所属批次”列维护，外部系统则使用其等价关联。规划中的任务可暂写“待分配”，实际开始前必须确定批次；跨多个独立批次的混合任务先拆分。

批次表不复制任务状态或另列成员清单。提交和 PR 引用批次及实际覆盖任务，集成记录关联版本与 PR；调整归属由协调者在任务表更新，涉及范围或验收变化时另记录批准依据。批次编号不代表依赖顺序，拆批次不能绕过阶段门槛。

推荐拆分方式：契约与测试、隔离纵向原型、默认关闭接入、生产回退验证。此例不是所有项目的固定阶段，不能覆盖已有门槛。

将“性能完成”拆为采集基线、批准阈值、满足阈值三个独立交付。等待阈值决策不能伪装成编码未完成，也不应阻塞无关任务。

## 需求顺序

总索引用优先级表达先做谁，用任务级依赖表达何时能开始。不要用递增 ID 暗示执行顺序。

先区分简单任务和复杂需求。简单任务直接执行和验证，不创建需求、批次和流程目录；已有复杂需求的子任务沿用原 ID。复杂需求通过项目 AGENTS 短引用或派发路径读取主协调 `.dev-work/workflow.md`，确认唯一索引和写入者。不同协调者申请串行分配 ID，子工作区不建索引；未获准读取时回问主 Agent 或接收标明版本的必要摘录，不假装本地资料对所有机器可见。

规划时检查依赖环：若 A 等待 B，B 又必须等 A 完成，先提交边界修订建议。批准前保持相关任务阻塞，不虚假勾选，也不自动放宽验收。

## 历史长文迁移

只在获得整理授权后执行：

1. 记录当前权威来源、主协调位置、代码分支、业务与文档各自未提交状态和现有链接；不因新版默认 `.dev-work/` 就另建状态表。
2. 从实际实现及证据盘点产物；历史聊天只作为线索。
3. 沿用已有需求 ID；确需新 ID 时通过索引写入者登记。拆分需求、设计、任务与验证材料，保留必要技术内容。
4. 将“部分完成”拆为可验收已交付项和独立剩余项。不能确认的产物标待验收，不直接标已完成。
5. 核对新表是否覆盖原范围、验收及延期内容，防止迁移时静默删除要求。
6. 新模型迁移需明确批准：保全旧材料和原约束，在主协调位置准备唯一资料，设置业务忽略规则及 AGENTS 短引用；已跟踪材料的停止跟踪或删除另按授权，不用 `.gitignore` 伪装迁移完成。
7. 由索引写入者更新导航，确认主资料可访问后按 [权威来源交接](collaboration.md#权威来源交接) 宣布生效；旧入口可保留迁移指引，不继续维护旧状态表。已有子 worktree 中的历史材料只按批准方式处理，不能擅自清理；后续新子工作区不复制或初始化流程目录。

## 版本证据

业务代码已提交时记录项目、分支及代码 SHA；未提交时记录工作区、时间、受影响文件和可用差异标识，不能将 HEAD 冒充实际快照。非 Git 业务项目记录文件范围和可用校验标识。文档版本单独记录可选独立文档仓库的分支/版本或本地未提交状态，文档 SHA 不证明业务代码通过验证。

进一步编辑后，旧证据只证明旧快照。至少重跑受影响测试；不能凭同一分支名宣称结果仍有效。

主 Agent 汇总子 Agent 报告并记录证据，子 Agent 不写 `.dev-work/`。独立文档仓库不参与业务 PR 合并，资料备份与业务代码推送是两个不同交付；清理任何承载唯一资料的工作区前都要核查可恢复性。

## 状态流转

通常为待开始 → 进行中 → 待验收 → 已完成。任何未完成任务均可因实际原因转阻塞，解除后回到适当状态。已完成任务若发现原验收不成立，明确重新打开并保留原因，不改写历史测试结果。

取消必须说明范围决策及原因；不能通过取消隐藏未修复的必要安全问题。
