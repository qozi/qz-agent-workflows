# 需求开发协作工作流

## 目标与边界

让维护者从一个入口知道有哪些需求、先做什么、当前任务、阻塞和交付证据。适用于不同项目、语言和 Agent 平台。加载 Skill 用于判断流程，不等于每个任务都要初始化工作流。

本 Skill 是执行约定，不是权限锁、自动初始化程序或 CI。不得声称它能自动阻止并发写入、虚假验收或越权操作。遵守平台权限、用户明确授权和项目约束；冲突时不通过本 Skill 绕过限制。

以真实项目验证本 Skill 时，区分主任务（工作流验证）与样本任务（项目整理）。试点完成后回到主任务复盘；用户问“下一步”时沿用该主线，不能仅因样本任务表存在未完成项就转为业务开发。复盘区分规则缺口、执行偏差与工具误报，检查维护成本和可恢复性，不以文档或任务数量证明成功。

## 首次动作

在编写代码或新增需求文档前：

1. 阅读项目入口规则及已登记的开发规范、项目架构，判断项目是否由 Git 管理；是 Git 项目才检查分支、状态和现有 worktree。涉及多个项目时先确认各自业务职责及关联。非 Git 项目不为使用工作流而擅自初始化业务仓库。保留他人修改，不执行破坏性清理。
2. 先识别咨询、简单任务、新复杂需求或继续开发。只有完整流程才定位主协调工作区的 `.dev-work/workflow.md`、总索引及写入者；简单任务不因资料不存在而初始化。子 Agent 优先使用派发消息给出的资料根目录，不在自己的 worktree 寻找或补建副本。
3. 已有需求必须恢复原 ID、权威文档来源、代码分支、任务和可用 Agent，不重复初始化。多个候选无法判断时只询问关键问题。
4. 确认用户允许的操作。开发授权不等于提交、合并、发布或清理授权；遵循更严格的现有约束。
5. 开始复杂需求时，简要报告需求 ID、权威文档来源、代码分支（非 Git 项目不适用）、当前任务、主协调者、阻塞和授权边界。此报告不是另一份持久任务表。

### 轻量与完整流程

| 类型 | 判断依据 | 执行动作 |
| --- | --- | --- |
| 咨询 | 代码解释、方案或流程讨论 | 只回答或检查，不自动建档、改代码 |
| 简单任务 | 目标明确、影响局部、少量步骤即可实现和验证，无重要跨模块依赖 | 直接开发和验证，不创建需求 ID、需求目录和批次，默认不用 worktree |
| 复杂需求 | 步骤较多且有依赖，改动范围大、跨模块、多阶段或重要架构/迁移风险，需要持续协作验收 | 按需初始化或恢复完整流程 |

不能仅凭改动行数或使用了多个 Agent 就判为复杂。边界不清时简要说明判断，只询问影响流程的关键问题；简单任务执行中发现重大依赖或范围扩大时再升级，避免先造文档再找任务。已有复杂需求内的小任务沿用原任务记录，不重复建档。

## 文档归类

本 Skill 只约定开发变更材料，不调整项目产品文档布局。新版默认只在指定主协调工作区保留一份 `.dev-work/`，排除在业务 Git 之外；可经用户选择成为独立文档 Git 仓库。主协调工作区是资料维护位置，不要求其代码签出 main，也不要求每个需求各建一套资料：

```text
.dev-work/
  workflow.md                      本项目协作说明、资料定位及授权约定
  README.md                        共享资料入口、需求索引、优先级及权威来源
  development.md                   开发规范；已有规范时只登记原路径
  architecture.md                  项目架构与业务职责；已有资料时只登记原路径
  R001-short-name/
    README.md                      需求身份、范围摘要、负责人和导航
    requirements.md                目标、非目标和需求验收条件
    design.md                      架构、取舍、阶段边界
    tasks.md                       唯一细粒度任务状态
    verification.md                版本化验证和审查证据
```

仅在复杂需求实际需要时创建相应文件；较小的复杂需求可只用 README 和任务表。模板是骨架，不是必须填满的表单。长期技术契约沿用项目约定位置，由需求文档链接，不复制全文。

业务项目的 `.gitignore` 加入 `/.dev-work/`，正确文件名是 `.gitignore`。忽略规则不移除已跟踪文件；发现旧材料已进入业务 Git 时先提出迁移及停止跟踪方案，取得批准后再处理，禁止直接 `git rm`、删目录或强制暂存。独立文档仓库初始化、边界检查及项目入口引用见 [接入说明](references/adoption.md)。

项目 `AGENTS.md` 保留工具 init 产生的项目职责、环境、命令和架构信息；本工作流仅增加对 `.dev-work/workflow.md` 的短引用，不塞入整套协作规范。子 worktree 中引用目标不存在是预期情况，按派发的主协调资料位置读取，不补建目录。

`development.md` 和 `architecture.md` 是跨需求共享资料，不是每个需求都生成一份：

- 初始化前先查找已有规范与架构资料。已存在时，在 `.dev-work/README.md` 登记真实路径即可，不要求再创建这两个文件，也不复制内容。
- 资料缺失时按需从模板补建。开发规范涵盖代码约定、验证命令、协作与集成约束；项目架构先解释业务职责，再解释模块、接口和依赖，不能只罗列技术栈。
- 多项目协作时，逐项记录项目标识、仓库或根目录、负责的业务、职责边界、上下游与接口，以及该项目规范和架构的来源路径。不清楚的职责明确标记待确认，不凭目录名猜测。
- Markdown 链接相对于所在文件，权威文档定位路径相对于资料根目录；指向业务文件时注明项目标识、业务根目录相对路径及必要代码版本，不能把 `.dev-work/` 当业务仓库根。跨机器用独立文档仓库标识或外部入口定位；同机派发另给可访问的绝对资料路径，不只给不可解析的符号名称。
- 每个需求只声明本次涉及的项目和变更边界，并引用共享资料。多个仓库共用需求时指定一个权威需求入口，其他仓库链接到它，不各自维护同一任务表。

原始测试输出、对话、调试截图不默认提交。保留可复现命令、关键结果、审查结论和必要证据；不记录密钥和敏感载荷。

模板位于 [templates/](templates/)。现有长方案的迁移流程见 [references/lifecycle.md](references/lifecycle.md)。未经要求，不顺便搬迁历史文档。

## 唯一事实来源

每个需求只指定一个细粒度状态来源：主协调文档中的任务表或用户指定的外部任务系统，二选一。

- 未单独使用 Git 时，登记项目标识、资料根目录与任务表相对路径，并在运行交接给出实际读取位置；本地资料不自动共享、备份或跨机器可见。
- 独立文档 Git 仓库启用后，文档身份为“文档仓库 + 文档分支 + 相对路径”，运行时另登记可访问工作区；未提交资料明确为工作区快照，不能用文档 HEAD 冒充。代码分支、代码 SHA 和文档版本分开记录。
- 切换或合并业务代码分支不会迁移、恢复或合并 `.dev-work/`；不把业务 main 当文档来源，不在子 worktree 双向同步资料。
- 总索引只维护需求级优先级、依赖和阶段，不复制任务完成状态。外部看板为权威时，仓库仅保留链接，不维护第二套实时清单。
- 权威来源变更必须显式交接。不要根据“文件更新更晚”自动选择来源。
- 旧项目仍使用 `.dev-changes/`、业务分支内的 `dev-changes/` 等材料时，先按旧权威来源恢复，迁移需单独批准，不自动启用第二份 `.dev-work/`。

### 项目总索引

- `.dev-work/workflow.md` 登记权威资料根目录、总索引、持久维护者、运行登记位置和可选文档仓库信息；项目 AGENTS 只引用该说明。子 Agent 从派发消息解析主协调来源，不假定业务 main 或当前 worktree 包含索引。
- 总索引同时只有一个指定写入者，可由项目维护者或指定协调者承担。需求协调者向其申请登记、ID 分配和导航更新；只有同时被指定为索引写入者时才可直接修改总索引。
- 先在权威索引串行确认 ID 和需求位置，再并行。参与者通过获准的只读路径、文档仓库或外部系统读取；未获准访问时由主 Agent 提供标明版本的必要只读摘录，不能凭空宣称共享可见，也不能在子 worktree 另建权威资料。
- 索引来源或写入者不明时，先只读查找并请求指定；派发不完整就回问主 Agent，不在多个工作区分别初始化。资料根目录自身迁移时更新协作说明及运行派发位置，必要时更新项目入口短引用。
- 索引只记录导航和需求级信息，不复制任务状态。新模型的需求链接位于同一文档根目录，不按业务开发分支拆成多份。

## 初始化与恢复

初始化是检查后执行的幂等流程，不是无条件生成文件：

1. 先完成任务分流；轻量任务到此不初始化。复杂需求定位主协调资料和写入者，检查已有 ID、任务或代码关联。子 Agent 不执行项目工作流初始化。
2. 新需求由需求协调者向索引写入者申请未使用的稳定 ID 和登记；并行分配需串行确认，不能仅扫描本地后就假定唯一。
3. 确认开发规范和架构资料的已有路径或必要补建内容；明确涉及项目的业务职责、本次范围、非目标、验收、优先级及具体依赖。编号和目录顺序不代表开发优先级。
4. 指定主协调者、唯一资料根目录、任务来源、代码分支及首个交付批次。是否使用 worktree 与是否开启文档 Git 是不同决定；worktree 必须先征得用户确认，文档 Git 仅按用户选择初始化，不擅自执行任一项目的 `git init`。
5. 完整初始化授权覆盖时，主 Agent 按接入流程设置业务忽略规则、协作说明及 AGENTS 短引用，按需创建材料。由索引写入者确认登记可见；已有内容只补必要字段，不覆盖或重新编号。无 Git 项目不需要 `.gitignore`，可选文档 Git 不会把业务目录变成 Git 仓库。

恢复时读取任务表和对应版本证据，并核对当前代码。聊天记录与代码不一致时先核验，不凭历史总结直接标完成。

## 旧任务整理与接管

用户指定旧方案、任务文档、交接记录、需求目录或 worktree，要求规范化或接手时，读取 [references/takeover.md](references/takeover.md)。支持“仅检查”“仅整理”“整理并继续”三种模式；未明确模式默认仅检查，不因提供路径就自行开始开发。

可通过自然语言调用，也可使用 OpenCode `/dev-takeover` 命令。命令只是调用同一工作流的入口，不是独立任务系统或自动迁移程序。整理必须保留原需求到新任务的映射，核验代码和证据后定状态；接管需明确协调者交接，不能抢占仍在执行的旧 Agent。

## 可执行任务

使用稳定任务 ID，例如 R001-T01。每项必须有独立交付、前置依赖和可验证的完成条件。

批次使用稳定 ID，例如 R001-B01；主协调任务表用“所属批次”列唯一维护任务归属，需求 README 只定义批次目标、依赖和验收，不另列任务状态或重复维护成员清单。开始任务前明确所属批次；一个任务跨多个独立批次时先拆分。外部任务系统为权威时使用其等价关联，不在本地另建平行状态表。

状态仅使用：`待开始`、`进行中`、`待验收`、`已完成`、`阻塞`、`已取消`。

- 不使用“部分完成”作为可执行任务状态。大阶段展示完成数量，混合任务拆为已交付项与独立剩余项。
- 一个任务若必须同时等待实现、维护者决策和生产接入才能结束，应拆开这些交付。
- `进行中`只代表已实际开始；实现完但未核验证据为`待验收`。
- `已完成`必须满足事先约定的条件且有版本化证据；未执行的测试、仅静态审查、原型性能不得冒充生产验收。
- `阻塞`必须写明缺少什么、解决责任方、解除条件及可并行任务，不允许只有“待确认”。
- 提交、合并、启用和发布单独记录，不与开发状态混用。任务完成不意味着已合并。
- 新发现的必要安全问题应先处理或显式阻塞；新增需求不得悄悄加入旧验收条件，需记录范围变更。

阶段门槛不得循环依赖。例如隔离原型不能同时禁止生产接入又要求实际生产回退。出现冲突时提出边界调整，取得批准后修改计划；不能自行降低门槛或无限追加原型。

## 协调与 worktree

每个需求同时只有一个任务表写入者。需求 README 记录持久负责人和协调规则；运行中的 Agent ID、workspace ID、机器路径放平台登记或交接消息，不反复写进版本历史。

协调者负责拆分、任务表、集成和验收组织。实现 Agent 只修改分配范围并回报证据；审查 Agent 报告问题和复核结果，不自行宣布整个需求完成。

只有指定协调者可更新任务状态；其他 Agent 发变更建议。更换协调者需停止旧写入者、核对未完成工作、明确接任者。记录声明不是文件锁；有实际并发冲突时暂停相关写入并协调。

主协调 `.dev-work/` 中的状态和记录由主 Agent（指定协调者）更新。实现、审查子 Agent 只读对应要求，完成后回报变更、实际验证和问题，由主 Agent 核验并写入任务表及 verification；子 Agent 不直接写资料目录，也不提交独立文档 Git。长期业务文档仍可按文件范围分工，涉及范围和验收调整须批准。索引和共享架构维护权不因承担子任务自动取得。

只有业务项目已由 Git 管理且存在大改动隔离、多需求并行或实际冲突风险时，才建议 worktree；独立审查和多个 Agent 本身不是自动创建理由。先说明必要性、基线、拟用分支、工作区及集成方式，询问用户确认；本轮已有明确同范围授权可复用并报告，不反复询问，不将普通开发授权视为 worktree 授权。非 Git 项目不使用 worktree，用户不采用时在明确文件分工的现有工作区执行，冲突不可避免则串行。

创建子 worktree 前检查脏改动和基线，未提交代码不会自动进入新工作区。子 worktree 仅承载业务代码，不创建、复制、软链接 `.dev-work/`，不创建独立文档 Git。若旧业务提交仍跟踪流程材料，先解决授权迁移或由用户裁定，不静默复制旧体系。派发必须给出主协调资料的实际只读位置；详细创建、汇报及清理规则见 [协作说明](references/collaboration.md)。共享工作区只有指定集成者执行 Git 写操作，冲突修改先串行或征求隔离授权。

## 验证、集成和收尾

1. 以可独立验收批次推进，不让整个大需求长期积累未提交内容；无提交授权时保留现状并说明风险，请求授权而不是擅自提交。
2. 先检查差异、必要测试及审查结果，再更新状态。测试运行期间代码有变化，应重跑受影响验证。
3. 主 Agent 记录业务代码 SHA 或未提交快照、命令、结果、范围和限制；文档仓库提交不能代替代码版本。旧结果不能直接沿用为新版本通过。
4. 一个批次可含多个相关任务和提交，经授权通过 PR 合并，不要求每个 commit 单独合并。
5. 合并 main 不等于启用生产；默认关闭实现的集成必须有明确批准的批次边界与真实能力声明。
6. 业务批次合并后，只更新主协调资料中的代码交付位置和证据，不把 `.dev-work/` 合并进业务 main。文档提交与业务提交分别授权、检查和记录；资料根目录或文档仓库变更才按 [交接流程](references/collaboration.md#权威来源交接) 迁移资料。旧版业务分支内资料另按批准方案处理。
7. 删除 worktree、删除分支、归档平台工作区分别获得必要授权；先保全代码、未跟踪产物和必要证据，停止 Agent 与服务。主协调资料目录被业务 Git 忽略，不能以代码工作区干净就视为可删；文档 Git 的本地提交也不等于已有异机备份。清理不能删除唯一资料根目录，必须先可靠保全并确认接任读取位置。
8. 交付报告只列完成项、实际验证、剩余阻塞和产物位置；业务开发的下一步从权威任务表选择，不另写新清单。仅检查、仅整理或工作流试点完成后，不自动切换为业务开发。

## 每轮检查

- 是否恢复了已有需求，而非重复创建？
- 是否先做轻量分流，避免简单任务建档？主协调资料、索引写入者、单一任务表及代码位置是否明确？
- 当前任务是否独立可验收、批次归属唯一、依赖可满足，共享文档写入范围是否明确？
- 状态是否有实际证据，测试是否对应当前版本？
- 是否只在 Git 业务项目中且经用户确认后创建 worktree？子 Agent 是否无流程目录、只读主资料并回报主 Agent？
- 是否未经授权提交业务或文档仓库、合并、发布或清理？
- 是否把原型能力、离线测试或配置校验误写成生产完成？
- `.dev-work/` 是否被业务忽略且未跟踪？资料是否独立于代码分支，清理时已保全且导航可恢复？
